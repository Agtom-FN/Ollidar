# E2 fixtures — small real-data slices for golden-dataset regression tests

Follow-up to S2-sim's own recommendation (REPORT.md §8/§9): "fold the real
indoor sample into E2 as a golden dataset for zero-point and tag handling."
This document covers all three fixtures produced, not just the indoor one.

Generated by `scripts/make_fixtures.py` from the public datasets in
`datasets/` (see `DATASETS.md` to re-fetch them — they are gitignored, ~1.3
GB total). Every fixture is real sensor data — no synthetic scene, unlike
`mid360_sim`'s procedural scan.

## Container format

All three fixtures share one format: `.livoxdump` (`scripts/livoxdump.py`),
the SAME container `tools/remote-capture/capture_mid360.py` already writes
for real remote-capture recordings, and the SAME format
`tools/remote-capture/verify_capture.py` already validates — so that tool
works on these fixtures unmodified as a structural sanity check, in addition
to `scripts/fixture_stats.py`'s content-aware stats.

Inside the container, each record's payload is a live-wire-format UDP
datagram byte-for-byte as it would appear on the real point/IMU ports: a
36-byte `DataHeader` + point/IMU payload, matching `sim/livox_wire.h`
exactly (same struct layout, same CRC32 algorithm). This means:

- `scripts/fixture_stats.py` and `sim/livox_wire.h`-based C++ code parse the
  same bytes.
- A future replay tool for these fixtures (a `.livoxdump`-input sibling of
  `replay/lvx2_replay.cpp`) needs no new wire-format code, only a different
  source reader — the two lvx2/livoxdump readers already share the same
  packet-builder helpers conceptually (`build_point_packet`/
  `build_imu_packet` in `livoxdump.py` mirror what `lvx2_replay.cpp` does in
  C++).

All three are comfortably under the 25 MB/file target.

### 1. `indoor_livox_5s.livoxdump` — the flagged no-return/tag distribution

First 5.00 s (by device clock) of `Indoor_sampledata.lvx2`, single device
(`47MDK9DF710030`), exactly as it appears in the recording.

```
$ python3 scripts/fixture_stats.py fixtures/indoor_livox_5s.livoxdump
  duration (dev clock): 5.00 s
  point packets       : 10,418  (bad dot_num: 0)
  points              : 1,000,128
  pts/s               : 200019
  no-return           : 35.24%
  tag histogram       : {0: 983484, 1: 5638, 2: 1549, 4: 3959, 5: 34, 6: 9, 8: 573, 9: 1, 16: 4607, 18: 1, 32: 273}
  IMU packets         : 0  (0.00 Hz)
  udp_cnt gaps (>1)   : 0
```

35.24% no-return matches the S2-sim spike's headline "35.9%" finding
(REPORT.md §5) to within the expected slice-to-slice variance — measuring the
**entire** 77.9 s indoor recording (not just this 5 s slice) gives 34.67%
zero-points, so both numbers corroborate the same real phenomenon:
`mid360_sim`'s procedural scan (0.0017% no-return) badly under-represents
real no-return/tag behaviour, which is exactly the gap this fixture exists
to close for A3's zero-point/tag filtering code.

### 2. `outdoor_livox_5s.livoxdump` — outdoor scene

First 5.00 s of `Outdoor_sampledata.lvx2`, filtered to a **single** device
(`lidar_id 738306240`, SN `47MDK9DF710030` — the same physical unit as the
indoor sample, for a clean indoor/outdoor comparison of the same sensor).
`Outdoor_sampledata.lvx2` is a genuine 3-device capture (see `DATASETS.md`);
interleaving all three into one fixture would triple both the size (past the
25 MB target for a 5 s slice) and the apparent no-return rate in a way no
single live driver socket would ever see, so this fixture deliberately keeps
one device's stream, matching what A3's driver actually consumes.

```
  duration (dev clock): 5.00 s
  points              : 1,000,128
  pts/s               : 200019
  no-return           : 67.76%
  tag histogram       : {0: 973187, 1: 471, 2: 96, 4: 958, 5: 14, 6: 3, 8: 77, 16: 16398, 32: 8924}
  IMU packets         : 0  (0.00 Hz)
```

67.76% no-return, much higher than indoor's 35.24% — expected: an outdoor
scene has far more out-of-range/sky returns than an enclosed room. Useful as
a second, harder data point for A3's zero-point filtering and for S3's
LOD/decimation tuning.

### 3. `outdoor_imu_ccby_6s.livoxdump` — synchronized IMU (the only committable one)

5.93 s window (bag offset 90.0 s–96.0 s, chosen to skip the recording's
startup/parking-lot segment) from the CC-BY-4.0 Zenodo rosbag
(`10.5281/zenodo.14841855`, Kenji Koide/AIST, "Driving SLAM test with Livox
MID360"). This is the only real dataset in this spike with **synchronized
IMU** (`DATASETS.md` §2), so it is the only one that can exercise A6/A7's
lidar-inertial front end end-to-end.

```
$ python3 scripts/fixture_stats.py fixtures/outdoor_imu_ccby_6s.livoxdump
  ports               : [56300, 56400]  packets/port [12500, 1200]
  duration (dev clock): 5.93 s
  points              : 1,200,000
  pts/s               : 202451
  no-return           : 41.74%
  tag histogram       : {0: 1194558, 1: 2341, 2: 156, 4: 2845, 5: 27, 6: 5, 8: 67, 10: 1}
  IMU packets         : 1,200  (200.20 Hz)
  udp_cnt gaps (>1)   : 3
```

200.20 Hz IMU and ~200k pts/s both match the rates `DATASETS.md` §2
independently measured for the whole 277 s bag (200.0 Hz IMU, 10.00 Hz ×
19,968 pts/msg ≈ 199,680 pts/s). The 3 small `udp_cnt` gaps are a known,
harmless artifact of this fixture's window-boundary handling (see "What is
real vs synthesized" below) — not a defect in the source recording.

## What is REAL vs SYNTHESIZED, and why

This matters for anyone using these fixtures to validate loss/skew/counter
logic, so it is stated plainly per fixture family:

**`indoor_livox_5s.livoxdump` / `outdoor_livox_5s.livoxdump`** (from `.lvx2`,
via `sim/lvx2_reader.h`'s Python port `scripts/lvx2_reader.py` — same
parsing logic `replay/lvx2_replay.cpp` uses, reused rather than
reimplemented):
- REAL, byte-for-byte from the recording: point x/y/z/reflectivity/tag,
  `udp_cnt`, `frame_cnt`, `data_type`, per-package device-clock timestamps
  (rebased to start at 0; real relative deltas preserved).
- SYNTHESIZED: the 36-byte `DataHeader` wrapper's `time_interval` (assumes
  constant 200,000 pts/s spacing — matches the recording's measured rate to
  five figures, see `DATASETS.md`) and `crc32` (not stored in `.lvx2`;
  recomputed over the real payload — note the SDK's own data-packet handler
  does not verify this CRC at all, only its control-frame path does, so this
  is for wire-format completeness, not because the SDK checks it).
- NOT PRESENT: IMU. Neither Livox sample file contains any (`DATASETS.md`
  §1: "Livox Viewer 2 does not write IMU packets into `.lvx2`"). These two
  fixtures are point-cloud-only by nature of the source, not a limitation of
  the extraction.

**`outdoor_imu_ccby_6s.livoxdump`** (from the Zenodo `rosbag2` `.db3`, read
with the pure-Python `rosbags` package — no ROS install needed):
- REAL: per-point x/y/z/intensity(→reflectivity)/tag from
  `sensor_msgs/PointCloud2` on `/livox/lidar`; full IMU vectors
  (angular_velocity, linear_acceleration) from `sensor_msgs/Imu` on
  `/livox/imu`; the message-level 10 Hz point-cloud cadence and 200 Hz IMU
  cadence (both taken from each ROS message's own header timestamp).
- SYNTHESIZED: `udp_cnt` (sequential counters assigned during extraction —
  the ROS `PointCloud2`/`Imu` message types carry no raw `udp_cnt` field at
  all, since `livox_ros_driver2` already decodes past it) and per-point
  timing *within* a 96-point packet (assumed even 200,000 pts/s spacing from
  each message's real 10 Hz header stamp). The **investigation note**: the
  raw ROS message does carry a per-point `timestamp` field, but its absolute
  scale did not reconcile with the known 10 Hz message cadence during
  validation (a message's min/max per-point timestamp span was ~390 µs, not
  the ~100 ms a 10 Hz cadence implies) — rather than guess at its semantics,
  extraction uses the message-level header timestamp plus a documented
  even-spacing assumption instead. The 3 `udp_cnt` gaps noted above trace to
  a handful of points right at the window's start boundary whose clamped
  timestamp ties broke strict `udp_cnt` ordering after the final
  point+IMU merge-sort — a fixture-generation edge case, not a real-data
  anomaly.
- Reflectivity: ROS `intensity` (float, observed range ~0–255 in this bag)
  is rounded and clamped to `uint8` to match the wire format.
- Trailing partial groups (<96 points) at the end of the extraction window
  are dropped so every packet in the fixture has `dot_num == 96`, matching
  the real wire format's invariant.

## Regenerating

```sh
cd spikes/s2-mid360-sim
# datasets/ must already be populated -- see DATASETS.md
python3 -m pip install rosbags numpy   # only needed for --zenodo
python3 scripts/make_fixtures.py --all
python3 scripts/fixture_stats.py fixtures/*.livoxdump
```

Or selectively:

```sh
python3 scripts/make_fixtures.py --indoor --outdoor      # fast, stdlib only
python3 scripts/make_fixtures.py --zenodo                # needs rosbags+numpy;
                                                           # unzips ~1.4 GB .db3 to a temp
                                                           # dir and deletes it when done
                                                           # (pass --keep-extract to keep it,
                                                           # or --zenodo-extract-dir to reuse
                                                           # an already-unzipped copy)
```

`--duration N` overrides the default slice length for all three;
`--zenodo-window-start N` moves the Zenodo window (default 90 s into the
277 s bag).

## Verifying a fixture structurally (bonus, from the shared container format)

```sh
python3 tools/remote-capture/verify_capture.py fixtures/outdoor_imu_ccby_6s.livoxdump --type mid360
```
